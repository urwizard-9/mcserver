# LGMC 프로젝트 진행·변경 통합 기록

기준일: 2026-11-08 KST. **전체 구조 → 구조별 변경 → 단계별 진행 → 결정·업데이트·검증 → 다음 작업** 순서로 읽는다. 설치·기동 성공과 실제 4인 게임 완료는 구분한다.

앞으로 진행 설명과 업데이트는 이 파일 하나에 기록한다. 현재 구조·진행 표는 최신 상태로 수정하고, 아래 날짜별 이력은 보존한다. 별도 날짜별 결과 파일은 만들지 않는다. 업데이트 제목은 `YYYY-MM-DD / 당일 순번 / 계획 단계 / 작업명`으로 통일한다. 순번은 문서 기록 순서이며 플러그인 버전이 아니다.

### 문서를 길게 반복하지 않는 관리 규칙

- 현재 구조·설명·단계 표는 새 버전을 밑에 복사하지 않고 해당 항목을 갱신한다.
- 날짜별 이력에는 변경된 내용만 기록한다. 형식은 **문제 → 근거 → 선택 이유 → 변경 위치 → 확인 결과·남은 한계**로 통일한다.
- 같은 작업의 연속 수정은 하나의 이력에 묶고, 이미 본문에 설명한 구조나 사용법을 반복하지 않는다. 이전 결정이 바뀌면 이전 이유와 변경 이유를 짧게 남긴다.
- 완료 단계의 오래된 상세 이력은 이 문서 안에서 요약한다. 중요한 결정 근거·검증 결과·실패·복구 위치는 유지한다. 문서 하나를 유지하되 작업 대화 전체를 누적하지 않는다.
- 소스·설정·해시·원시 로그는 해당 파일을 근거로 연결한다. 문서에 원문을 모두 복사하지 않는다. Git 커밋 이력은 실제 커밋이 생겼을 때만 근거로 사용하며, 현재 모든 변경이 커밋됐다고 가정하지 않는다.

## 1. 전체 구조부터 이해하기

### 실행 중인 시험 구성의 역할

Java 이용자는 Paper에 접속하고, 모바일 이용자는 Geyser·Floodgate를 거쳐 같은 Paper 월드에 들어온다. LGMC가 역할·낮밤·투표·승패를 처리하고, 별도 LgmcLobby가 준비·대기실·자동 시작을 담당한다. 두 플러그인은 같은 Paper 서버 안에서 실행된다. PC·모바일용 게임 서버나 게임 플러그인을 각각 만든 구조가 아니다.

현재 시험 서버는 봇·DB·Grafana 없이 실행한다. 향후 Discord 봇과 독립 제어 서비스, 관측 서비스는 게임 컨테이너 밖에 둔다. 그 운영 구조는 아직 구현하지 않았다.

### 폴더 전체 구조

아래는 주요 경로를 중심으로 한 구조다. `기존`은 보존된 원본, `추가`는 이번 전환에서 만든 소스·설정, `로컬`은 Git에서 제외하는 실행 데이터다.

```text
마크서버/
├── docker-compose.yml              # 기존: 원본 전체 서비스 구성
├── bot/                            # 기존: Discord 봇, 아직 개편 전
├── prometheus/                     # 기존: 원본 지표 설정
├── compose.trial.yml               # 추가: 독립 게임 시험 서버
├── .env.trial.example              # 추가: 공개 가능한 설정 예시
├── .env.trial                      # 로컬: 실제 설정·비밀번호
├── .gitignore                      # 수정: 실행 데이터·비밀정보 제외
├── README.md                       # 수정: 통합 기록으로 안내
├── config/                         # 추가: 버전·출처·해시 기록
│   ├── lgmc/lang/                  # 추가: 한국어 및 비교용 원본 언어 파일
│   ├── trial-artifacts.json
│   ├── geyser/item-correspondence.json # 조사용 아이템 대응표 (실행 매핑 아님)
│   └── maps/werewolf-trial.json
├── patches/lgmc/                   # 추가: 원본 LGMC 최소 수정 소스
│   ├── LICENSE / README.md
│   └── src/fr/lightshoro/lgmc/managers/
│       ├── ResourcePackManager.java
│       └── GameManager.java
├── lobby/                          # 추가: 별도 준비·대기실 플러그인
│   ├── README.md
│   └── src/main/
│       ├── java/local/lgmc/
│       │   ├── LobbyPlugin.java
│       │   └── PreviewMenu.java      # 읽기 전용 한국어 견본
│       └── resources/
│           ├── plugin.yml
│           ├── config.yml
│           └── messages.yml        # 추가: 대기실 한국어 문장
├── scripts/                        # 추가: 빌드와 파일 검사
│   ├── build-trial-plugins.py
│   ├── verify-trial-artifacts.py
│   └── ValidateTranslations.java    # 추가: 언어 키·치환값 검사
├── docs/
│   ├── PROJECT_LOG.md              # 현재 문서: 진행·구조·업데이트 통합
│   ├── phase-1-validation.md        # 시험 체크리스트
│   └── research/                   # 조사 근거·자산 목록
├── trial-data/                     # 로컬: 실제 게임 실행 데이터
│   ├── world/                      # 현재 무료 마을 맵
│   ├── plugins/                    # 실행 JAR와 플러그인 설정
│   ├── original-plugins/           # 원본·이전 시험 JAR
│   ├── lobby-build/                # 빌드 산출물
│   └── logs/                       # 게임 로그
└── backups/                        # 로컬: 변경 전 월드·설정 보관
```

### 코드가 실제 서버에 적용되는 흐름

`patches/`와 `lobby/` 소스 → `scripts/build-trial-plugins.py`로 컴파일 → `trial-data/lobby-build/`에 JAR 생성 → 서버 정상 종료 후 `trial-data/plugins/`에 설치 → 재기동·로그·기능 확인 순서다. 소스만 수정해도 실행 중 서버에 즉시 반영되지는 않는다.

`config/`는 출처와 버전 등의 관리 기록이고, 플러그인의 실제 실행 설정은 주로 `trial-data/plugins/`에 있다. `backups/`는 복구본이며 로그나 Git 소스와 역할이 다르다.

## 2. 전체 구조에 따른 파일·코드 변경

### 실행 구성과 버전 기록

| 경로 | 추가/수정 | 목적 및 동작 |
|---|---|---|
| compose.trial.yml | 추가 | 게임 서버 하나만 별도 실행. 기존 봇·DB·Grafana와 분리. 이미지 고정, Java 인증, 화이트리스트, 시험 포트, Adventure 모드, 명령 블록 제한, 로그 회전 설정 |
| .env.trial.example | 추가 | 실제 비밀번호 없는 시험 설정 예시 |
| .env.trial | 로컬 추가·Git 제외 | 실제 시험 환경 값과 RCON 비밀번호. 문서에 비밀값을 복사하지 않음 |
| config/trial-artifacts.json | 추가·갱신 | 플러그인 출처·버전·해시. 현재 수정 LGMC와 새 대기실 포함 |
| config/maps/werewolf-trial.json | 추가 | 맵 제작자·출처·원본 해시·백업 위치·12개 시작 위치 기록 |
| .gitignore | 수정 | 시험 데이터·비밀정보를 Git에서 제외하고 예시 환경 파일은 허용 |

### LGMC 원본 수정: 두 클래스

`patches/lgmc/src/fr/lightshoro/lgmc/managers/ResourcePackManager.java`

- 문제: Bedrock이 Java 팩을 받지 못하면 원본 LGMC가 추방했다.
- 변경: Floodgate API의 인증 UUID 판정으로 Bedrock 이용자를 확인하고 Java 팩 전송·상태 검사에서 제외한다. 이름 접두사만으로 판단하지 않는다.
- Java 이용자는 기존 팩 적용 경로를 유지한다. 이 변경은 Bedrock 전용 팩을 제공하지 않는다.

`patches/lgmc/src/fr/lightshoro/lgmc/managers/GameManager.java`

- 문제: 원본 시작 타이머를 외부에서 취소할 수 없고, 시작 직전 인원 부족 시 게임 상태가 잘못 남을 수 있었다.
- 변경: 시작 작업을 보관하고 cancelStart()를 추가했다. 중복 시작·4~12명·스폰 설정·카운트다운 중 참가 UUID 변경을 검사한다. 역할 배정 사전 조건을 통과한 뒤 게임 중 상태로 전환한다.
- 기존 10초와 전원 참가 방식은 유지한다. 역할·투표·승패 로직은 이번 변경 대상이 아니다.
- `patches/lgmc/LICENSE`는 원본 MIT 라이선스, README는 수정 범위와 빌드·복귀 안내다.

### 별도 대기실 플러그인

`lobby/src/main/java/local/lgmc/LobbyPlugin.java`를 새로 만들었다.

- UUID 기준 준비 목록과 입장별 마감 시간을 메모리에 관리한다. DB는 사용하지 않는다.
- 입장·퇴장, 준비·취소, 1초 주기 상태 확인을 처리한다.
- 기본 120초 미준비 강퇴, 30초·10초 경고, 준비 완료자 제외, 게임 중 강퇴 중지를 구현했다.
- 4~12명 전원이 준비하면 LGMC 시작 명령을 호출한다. 게임 상태는 공개 메서드로 읽으며 채팅이나 로그 문구에 의존하지 않는다.
- 입장·퇴장·준비 취소 시 시작을 취소하고 게임 종료 후 준비를 초기화한다.
- `/ready`와 `/lobby` 인벤토리 메뉴, 직접 시작 명령 차단, 대기 중 피해 방지·공허 복귀를 구현했다.
- 지원 LGMC 버전을 확인하며 다른 버전이면 대기실을 비활성화한다. 이 조합에 맞춘 시험 구현이며 범용 LGMC 연동 API가 아니다.
- 한국어 문장 21개를 messages.yml로 분리했다. msg()가 색상과 치환값을 처리한다. 운영 로그 및 콘솔 상태의 기계 판독용 필드는 유지한다. 실행 파일에 내장한 기본 문장으로 누락 키를 보완한다.

`lobby/src/main/resources/plugin.yml`은 플러그인 이름·버전·LGMC 의존성·명령 등록이다. `config.yml`은 준비 제한 시간과 대기 좌표의 기본 템플릿이다. 실제 실행 설정은 `trial-data/plugins/LgmcLobby/config.yml`이다. 템플릿 수정만으로 기존 실행 설정이 자동 변경되지는 않는다.

최소 4명·최대 12명과 지원 LGMC 버전은 현재 코드에 고정돼 있다. 모든 운영 숫자를 설정으로 분리한 상태는 아니다. 준비 취소 시 최초 마감 시간을 연장하지 않아 이미 120초가 지났다면 다음 점검에서 강퇴될 수 있다.

### 한국어 미리보기와 모바일 대응표

- `lobby/src/main/java/local/lgmc/PreviewMenu.java` 추가. 별도 InventoryHolder로 견본 메뉴를 구별하며 LGMC 원본 GUI의 투표·능력 콜백은 호출하지 않는다. 실제 한국어 키와 역할 설정의 아이템 종류를 읽어 견본을 만든다.
- `/lgpreview [player]`는 `lgmclobby.preview` 권한이 필요하고 기본은 관리자 전용이다. 대상 플레이어에게만 화면을 연다. 기존 PC 관리자 mosLu가 `/lgpreview .Lumos7886`으로 휴대폰에 열어줄 수 있다. 새 관리자 권한은 부여하지 않았다.
- 역할 9개의 제목/설명, 투표·마녀 견본, 밤낮·시작 안내, 마을 승리 견본을 제공한다. 모든 역할 능력 화면·승리 유형을 제공하는 완전한 복제는 아니다. 가짜 이름과 숫자를 쓰는 견본임을 알린다.
- 대기 상태에서만 허용하고 클릭·드래그·하단 인벤토리 이동을 취소한다. 개인 인벤토리/보조 손/준비 상태를 직접 바꾸지 않는다. 화면 전환은 클릭 처리 이후 다음 틱으로 미룬다. 시작 시 열린 견본을 닫고 플러그인 종료 시에도 닫는다.
- 미준비 제한 시간은 계속 적용된다. 두 계정 시험에서는 먼저 `/ready` 후 미리보기를 사용한다. 4명 이상 전원 준비 상태에서는 자동 시작하므로 이 시험은 2계정 대기 상태에서 진행한다.
- messages.yml에 미리보기 문구 16개를 추가해 총 37개를 관리한다. 기존 실행 문구는 보존하고 새 키만 추가했다.
- `config/geyser/item-correspondence.json`은 역할/표식 10종과 능력·메뉴·탈락 표식 13종, 총 23종의 조사표다. Java 아이템·언어 키·코드 출처·Java 모델·노출 주의·모바일 대응 미정 상태를 기록했다. Geyser가 읽는 실행용 매핑 파일이 아니므로 자동 설치하지 않는다.
- 확인된 예: 역할 카드=설정의 염료, 생명 물약=SUGAR, 독약=GUNPOWDER, 예언 수정구=FLINT, 사냥꾼 도구=WOODEN_HOE, 늑대인간 지정 도구=IRON_HOE, 유언장=WRITTEN_BOOK. 기본 아이템·CustomModelData·모델 컴포넌트의 적용 방식을 단정하지 않고 다음 견본 팩에서 확인한다.
- 근거: 원본 ConfigManager.getRoleHelmetItemStack은 설정의 Material로 아이템을 만들고 GameManager는 역할 카드를 보조 손에 지급한다. 그래서 일반 CustomModelData 예제를 그대로 복사하지 않고 실제 아이템 대응부터 조사했다.
- 한계: 견본에서 메뉴를 보는 것은 실제 게임·보조 손 은닉·팩 다운로드 검증이 아니다. 다른 사람에게 역할 카드가 보이는지 시험하는 장비 견본은 아직 구현하지 않았다.

### 한국어 설정과 표현

- `config/lgmc/lang/ko.yml`: LGMC 한국어 원본. 원본의 320개 문자열 키와 목록 요소 21개를 유지했다. 310개 문구를 번역하고 구분선 10개는 보존했다.
- `config/lgmc/lang/en-reference.yml`: LGMC 5.1.3 비교용 원본. 원본 라이선스는 `patches/lgmc/LICENSE` 참조. 번역 키·치환값 누락 검사의 기준이다.
- 실행 위치는 `trial-data/plugins/lgmc/lang/ko.yml`, 선택 설정은 `trial-data/plugins/lgmc/config.yml`의 `language: ko`다. LanguageManager가 기존 ko 파일을 읽는 것을 소스에서 확인해 추가 LGMC 클래스 수정 없이 적용했다.
- `lobby/src/main/resources/messages.yml`: 준비·강퇴·메뉴 문구 21개. 실행 설정은 `trial-data/plugins/LgmcLobby/messages.yml`이다. 수정 후 정상 재시작한다.
- 역할 이름은 늑대인간·주민·잠 못 드는 소녀·예언자·마녀·큐피드·사냥꾼·천사·도둑·촌장으로 통일했다. 게임 규칙은 그대로이며 PC와 모바일이 같은 번역을 사용한다.
- 작은 화면을 고려해 주요 메뉴 제목을 짧게 작성했다. 관리자 메뉴의 좌클릭·우클릭 안내는 원본 조작 구분을 보존했다. 모바일에서 실제 대응하는지는 화면·조작 시험이 필요하다.
- 언어 파일의 관리자 카운트다운 안내에 시험 구성이 10초 고정임을 명시했다. 설정 UI를 번역했다고 원본의 미사용 설정값이 작동하는 것은 아니다.
- `/lg help`, 스킨·이웃 진단, 일부 관리 재설정 문구와 빈 연인 채팅 안내 등은 원본 코드에 고정돼 있어 이번 언어 파일 번역에 포함되지 않는다. 원본 수정 범위를 늘리기 전에 실제 필요한 경로를 선정한다. 완전 한글화로 판정하지 않는다.

### 맵 교체는 실제로 어떻게 수행했나

핵심은 `trial-data/world` 교체가 맞지만, 실행 중 폴더를 덮어쓴 것은 아니다.

1. 맵 ZIP을 내려받아 해시와 내부 구성을 검사했다. 원본 level.dat 버전은 1.20.1이며 명령 블록 등도 조사했다.
2. 접속자에게 안내하고 시험 서버를 정상 종료했다.
3. 기존 월드·LGMC 설정·server.properties·화이트리스트를 `backups/before-free-map-20261107-084851/world-and-settings.tar.gz`로 보관하고 읽기·해시를 확인했다.
4. 기존 `world`, `world_nether`, `world_the_end` 폴더도 같은 백업 폴더로 이동해 보존했다. 기존 Nether·End를 새 맵과 섞지 않았으며 새 차원 폴더는 이후 서버가 생성했다.

## 7. 다음 작업 상세 계획: 미리보기 → 모바일 최소 팩 → 4인 실전

2026-11-07 계획 갱신. 작업 A의 기본 미리보기와 B의 1차 대응표는 구현·설치했고 클라이언트 시험은 대기 중이다. C~F는 다음 계획이며 아직 완료하지 않았다.

### 현재 번역 검증의 경계

341개 문자열·목록 요소의 구문·키·치환값과 서버의 ko 로드·일부 응답은 확인했다. 실제 역할 배정·밤낮·투표·승패 화면은 게임을 시작하지 못했으므로 미검증이다. 게임 없이 문장·역할 카드 견본을 표시하는 시험은 가능하지만, 실제 게임이 올바른 시점에 올바른 사람에게 보내는지는 4인 실전에서 확인해야 한다.

YAML(.yml/.yaml)은 Docker 전용이 아닌 범용 텍스트 데이터 형식이다. Compose는 서비스 설정을, Paper 플러그인은 설정·언어·등록 정보를 이 형식으로 읽는다. LGMC가 YAML 언어 파일을 읽도록 구현되어 있어 ko.yml을 선택했다. 대기실도 Paper의 YAML 기능을 사용하면 설정과 문장을 코드에서 분리할 수 있다. 실제 실행 로직은 Java/JAR에 있다.

### 목표와 연결 구조

LGMC의 실제 아이템 정의 → 자산 대응표 → Bedrock 그림·모델·소리 → 필요 시 Geyser 매핑 → 휴대폰 팩 적용 → 두 계정 표시·정보 은닉 시험 → 4인 역할·투표 검증 순서다.

Java는 기존 팩을 유지하고 모바일에 Bedrock 팩을 제공한다. 원본 LGMC의 게임 규칙과 4인 제한은 유지한다. 팩은 외형·소리를 담당하고 투표·능력의 성공 여부는 Paper/LGMC가 처리한다.

### 작업 A. 게임을 시작하지 않는 한국어 미리보기

- 관리자 전용 시험 도구로 번역 제목·안내·역할 이름·아이템 설명을 미리 표시한다. 가짜 이름·시간을 명확히 시험 값으로 사용한다.
- 게임이 대기 중이고 카운트다운이 아닐 때만 허용한다. 미리보기 메뉴의 아이템 이동·실제 투표·능력 처리를 막는다.
- 원본 /lg gui는 게임 참가 데이터가 없을 때 안전하지 않은 경로가 있어 그대로 재사용하지 않는다. 실제 GUI 구조와 문장 참조를 조사한 뒤 동작 없는 견본을 만든다.
- 제목/액션바는 호출자에게만 보여준다. 이후 장비 견본 시험이 필요하면 기존 인벤토리 복원·종료 시 정리를 설계하고 실제 사용 전에 백업한다.
- 완료: PC와 모바일에서 글자 깨짐·잘림·치환값 잔여를 확인하고, 미리보기 종료 후 준비 상태·인벤토리가 원래대로 유지됨을 확인한다.
- 한계: 실제 게임에서의 메시지 발송 시점·대상·비밀 채팅은 검증하지 못한다.

### 작업 B. 실제 아이템과 모바일 표현 대응표 확정

- 원본 코드의 역할 지급·GUI 아이템 생성과 Java 팩을 대조한다. 각 항목에 Java 아이템 종류, 모델/컴포넌트, 이름, 사용 위치, 공개 범위, 모바일 표현, 시험 방법을 기록한다.
- 단순 조사된 PNG 개수 전체를 변환 대상으로 삼지 않는다. 실제 사용하는 역할 카드·투표/기권·물약·유언장·사냥꾼 도구부터 선정한다.
- 원본 팩은 기본 염료 등의 모델을 덮어쓰므로 CustomModelData 기반이라고 가정하지 않는다. 기본 텍스처 교체로 충분한 항목과 별도 매핑이 필요한 항목을 구분한다.
- 완료: 게임 필수 표현 목록과 대응 방식이 정해짐. 개인 역할을 다른 사람에게 드러내는 표현은 별도 필수 시험으로 지정.

### 작업 C. 자산 이용 조건과 최소 견본 팩

- 원본 CDN 팩의 변환·배포 조건을 확인한다. LGMC 코드의 MIT만으로 별도 이미지 이용 조건을 확정하지 않는다.
- 확인되지 않으면 임시 자체 기호·색상·문자 카드로 기술 시험을 진행하고, 원본 이미지 재배포는 하지 않는다. 제작자에게 연락하는 것은 사용자의 별도 지시 없이 수행하지 않는다.
- 처음에는 카드 1~2개로 manifest·식별자·버전·텍스처와 필요한 모델/매핑을 구성한다. 정확한 매핑 형식은 설치 Geyser 빌드가 지원하는 것으로 검사한다.
- 완료: 폰에서 팩을 내려받아 재접속해도 견본이 정상 표시되고 Java 화면은 기존대로 유지됨.

### 작업 D. 비밀 역할 표시의 안전성 우선 시험

- 역할 카드가 본인의 인벤토리/손에서 구별되는지, 다른 계정의 화면에서는 역할이 드러나지 않는지 확인한다.
- Java→Bedrock, Bedrock→Java 관찰 방향을 바꿔 시험한다. 손·보조 손·3인칭 표시를 확인하고 드롭·장비 교체 등 노출 경로는 실제 게임의 제한과 함께 조사한다.
- 기본 아이템 전체의 외형을 바꾸는 방법은 같은 종류의 다른 아이템에도 영향을 줄 수 있어 별도로 확인한다.
- 은닉이 실패하면 나머지 카드를 일괄 변환하지 않는다. 매핑/모델 수정, 본인 전용 메뉴 표현 등 대안을 검토하고 필요한 LGMC 수정 범위를 다시 명시한다.
- 완료: 두 계정 방향 모두 본인 구분·상대 은닉이 확인됨. 4인 역할 선택·관전 시 은닉은 이후 실전 시험으로 남김.

### 작업 E. 필수 팩 확대와 배포·복귀 준비

- 견본 시험 통과 후 필수 역할·능력 아이템으로 확대한다. 플레이어 머리·GUI가 기본 Geyser 표현으로 충분하면 불필요한 대체물을 만들지 않는다.
- 소리는 원본 이벤트와 모바일 대응을 확인한 뒤 반영한다. 기본 소리로 기능 전달이 가능한지 먼저 확인한다.
- 팩 버전·UUID·해시·매핑을 함께 관리한다. 초기 폴더 예정은 resource-packs/bedrock/, config/geyser/, 검사용 scripts/다. 확정 구조는 대응 방식 결정 후 통합 문서의 구조도에 반영한다.
- 실제 배치는 trial-data/plugins/Geyser-Spigot/packs/ 및 필요한 매핑 위치다. 서버 파일 백업·정상 종료·배치·재기동·다운로드 확인 순서로 적용한다.
- 팩 수락·거절·다운로드 실패·재접속·캐시 갱신을 각각 시험한다. 필수 팩의 적용 강제 여부는 기능 의존성을 확인한 후 결정하며 최초 견본부터 강제로 추방하지 않는다.
- 완료: 두 계정에서 핵심 구분·메뉴 조작·팩 갱신 확인. 이전 팩·매핑으로 되돌릴 자료 확보.

### 작업 F. 4인 검증 및 다음 운영 단계로 이동
